Agni Bot — Blueprint v3

Status note (2026-10-26): Agni Bot is a messaging app for named, specialised bots, with performance ahead of UI polish. The project is source-available, not open source. Section 10 records what is built as of 2026-10-26.

Our own speed-first harness · our own server on bb-1 · our own Mac and Android apps over Tailscale · free model tiers with failover · ACP only for subscription lanes. Supersedes Blueprint v2 (OpenCode-as-engine).

2026-10-16 · prepared for Nachiketh · evidence: live API tests and official docs retrieved today. Sources in the footer.

0 · Verdict

Agreed on all three calls — and one of them is now backed by hard evidence. (1) OpenCode steps out of the engine seat: we build our own thin, speed-first harness. (2) No Resend, no custom-domain email — a Gmail account is the agent’s mailbox, full stop. (3) We build our own clients: one codebase producing a clean black Mac app and an Android app, talking WebSockets to your server over Tailscale.

The thing that made “OpenCode as the engine” attractive was its free models without an API key. I tested that directly today: the model list is public, but calls are refused —

{"error":{"type":"FreeTierError","message":"OpenCode's free tier can only be used from within OpenCode."}} live HTTP 403, 2026-10-16, no-auth call to opencode.ai/inference with a free model

So instead of depending on a free tier that is deliberately locked to another product, we source free capacity from providers that are meant to be called by API — and everything below stays $0.

We buildThe harness (agent loop, tools, memory), the server (Bun + SQLite + WebSocket), and both apps (Tauri 2 shared codebase). Small on purpose.
We adoptModel APIs (NIM, Groq, Cerebras, Gemini, OpenRouter free, local LM Studio), Gmail (app password over IMAP/SMTP) + Calendar (private ICS), Tailscale, ntfy for push, MCP for tool servers (REA), ACP for Codex and friends.
We refuseAnother general-purpose coding harness. No LSP, no repo indexing, no IDE features — coding jobs are delegated through ACP to Codex/Claude/Cursor where those habits already exist.

2 · The speed thesis — why ours will be fast

Your requirement is the specification: “a quick question should answer quickly, not go search a pile of memory files first.” Every mechanism below exists because a coding harness has the opposite priority — it optimizes for workspace depth, we optimize for conversation latency.

RuleWhat it preventsHow we implement it
S1 · Constant promptPrompts growing with history and memorySystem + persona + rolling summary + last ~8 turns. Hard token ceiling per turn; memory never rides in the prefix.
S2 · Memory is a toolEvery question paying for everything ever savedSQLite FTS5 behind memory.search / links.search / tasks.list; the model retrieves only when the question needs it.
S3 · Lane isolationLong jobs blocking quick questionsInstant lane (one call, no tools, ≤1.5 s p50 target), task lane (tools, steps, approvals), deep lane (parallel subagents + search). Separate worker pools, priorities.
S4 · Write-time workRead-time scans and summarizationSummarize and index at ingest (link fetched, mail arrives, note written). Briefs are precomputed by cron at 07:55, not assembled on demand.
S5 · Warm pathCold first-token after idleKeep-alive prefill pings on the active persona’s provider (cheap/free models), stable system prefixes for prompt caching where the provider supports it, connection pooling.
S6 · Perceived speedNetwork round-trip feelLocal echo on send (<30 ms UI ack), token streaming into the bubble, tool activity strips, optimistic completion markers. Tailscale keeps the socket private and direct.
S7 · Bounded everythingRunaway loops that make the assistant feel stuckPer-turn step budget, tool timeouts, cancel button that actually interrupts, per-day cost/token caps with graceful fallback to a smaller model.
Honest stop rule: if after P0 tuning the instant lane’s p50 exceeds ~2.5 s server-side on Groq/Cerebras-class models, we pause and re-measure before building further — the whole point is speed, and the plan should prove it early or change.

3 · Architecture

4 · Server core & protocol

StackBun + TypeScript (fast startup, built-in WebSocket, bun:sqlite with FTS5). One process: agents, router, tools, queue, cron. Container-friendly for bb-1.
StateSQLite (WAL) for threads, messages, memories, links, tasks, jobs, costs, approvals. Nightly .backup to a second file; no external database.
AuthPer-device tokens minted by QR pairing in the app; server binds to the Tailscale interface only; everything else denied at the firewall.

Wire protocol (typed frames, versioned — this is the contract between server and both apps):

client → server hello {token, device} resync {lastSeq} msg.send {threadID, text, files} msg.cancel {turnID} approve.reply {requestID, once|always|reject} agent.select {agentID} thread.open {threadID} server → client hello.ok {serverTime, seq} token {turnID, delta} turn.start | turn.end {stopReason, usage} tool.start | tool.update | tool.end {callID, name, preview} approval.request {requestID, action, preview, buttons} form.request {question, options} notify {title, body, sound} agents.update | presence | error {code, retryAfter}

5 · Agents, threads, connections

  • Agents are personas, not processes. Each has a name, avatar color, one model (or model ladder), a short system prompt, a tool allowlist, and optional memory scope. The sidebar is the roster only; the chat surface is one conversation per agent — you talk to Agni in one enduring surface, like texting a person, not a wrapper with a sessions list. /new starts a fresh session block inside that same surface: the model's context is cleaned (closed block compacted into a bounded carried summary), while the transcript above stays part of the same conversation. Session blocks auto-roll at context pressure. Background results (briefs, reminders) land as their own session blocks in the same conversation; rich output renders as an HTML artifact page.
  • Agent-to-agent work is explicit. Any agent can spawn a subagent (task lane) or hand a coding job to an ACP harness (Codex first). Subagents render as nested activity strips inside the thread — you always see who did what.
  • Connections page. One screen listing Gmail, Calendar, MCP servers (REA is already wired), model providers (with live health), and ACP harnesses (login status, quota hints). Toggling a connection is a tap; broken connections show a fix action.
  • Conversations survive everything. Server restarts, app restarts, phone switches: the stream reattaches via resync, the conversation and its session blocks reattach via SQLite, and mid-turn streams continue. The CLI keeps its thread commands (its blocks are the same rows); the apps don't show them.

6 · Memory, links, tasks — the three stores

StoreCapture (typed into the app or forwarded)Retrieval & rituals
MemoryFacts you want kept: “remember: my passport expires Mar 2029”. Written raw + indexed immediately; long items get a one-line summary at write time.memory.search tool; agent checks it only when relevant (S2). Weekly: agent proposes 3 memories to merge or drop — you tap approve.
LinksPaste any URL (chat or share-sheet later). Server fetches title, 2-line summary, tags — at write time.“find that article about Postgres pooling” → links.search → link card with your original note. Weekly: 3 old links resurfaced with a why-now line.
Tasks“add task: renew insurance by Nov 30” — a tiny parse writes title/due/priority/status. No LLM loop needed for capture.“what’s on today” + the 07:55 brief (precomputed). Snooze/done as one-tap actions; overdue items escalate gently, not repeatedly.

7 · Apps (Mac + Android)

  • One codebase, two targets: Tauri 2 (Rust shell + web UI) builds the macOS app and the Android app from the same source — the fastest honest path to “clean, good, black” on both without writing Swift and Kotlin separately.
  • Chat surface: streaming text, code blocks, tool activity strips, approval buttons, inline rich blocks — including HTML charts — as a fast-follow feature (the webview renders them natively, we sandbox each block).
  • Design constraints: true black theme by default, thumb-reachable primary actions on Android, keyboard-first on Mac (⌘K to switch agent, ⌘N new thread), no nested navigation mazes.
  • Push: desktop notifications natively on Mac; on Android, ntfy (self-hosted on bb-1, free, no account on public servers) delivers briefs and pings; the app itself shows in-thread activity.
  • Pairing: app shows a QR from the server (bun run pair); scanning installs the device token. Revoke from the server at any time.

9 · Email & calendar (Gmail-first, no Resend)

  • The agent’s mailbox: hey.agnibot@gmail.com — created 2026-10-16. Still to do on it (your side): 2-Step Verification, recovery email/phone, signed in on your phone. The server reaches it over IMAP/SMTP with a Gmail app password — verified today: app passwords are still supported, and this skips the OAuth trap for personal projects (apps left in “Testing” get refresh tokens that expire every 7 days; publishing with Gmail scopes means Google’s verification review).
  • Durability: Google deletes accounts only after two years of zero use, and its policy counts reading or sending email as activity (checked today) — a working mailbox never trips it, and keeping it signed in on your phone is belt-and-suspenders. The server also files every message into your own SQLite, so the archive outlives Google policy changes.
  • Read & draft: the agent watches its inbox (IMAP IDLE / 2-minute polling — free), summarizes what matters, and drafts replies. It signs up for services as hey.agnibot+servicename@gmail.com (plus-addressing: one inbox, filterable, leak-traceable); verification codes land in the thread; CAPTCHAs are your 10-second tap.
  • Send discipline: sending is always approval-gated for the first weeks; “always allow this sender” unlocks trusted flows later; volume stays personal-scale, far under Gmail’s limits.
  • Your mailbox: optional second connection with its own app password, read + draft only. “Reply to Sarah about Thursday” produces a draft you approve — it sends from your account from the app. No raw forwarding (that just recreates inbox noise); Gmail’s delegate access covers peeking any time.
  • Calendar: reads come from Google Calendar’s private iCal link (free, no OAuth); writes arrive as one-tap “add to calendar” invites Agni emails you. The full Calendar API would mean Google verification — skipped on purpose. The brief still knows your real agenda.
  • theynr.xyz (optional vanity): registered through a free-domain program (the Gen.xyz family) — if you find that login, its DNS panel can point MX records at a free forwarder (ImprovMX free plan verified today: 1 domain, 25 aliases, 500 forwards/day) and hey@theynr.xyz lands in Agni’s inbox. Receive-only — sending as a domain is paid-only on every free tier, so sends always come from the Gmail address. When the domain lapses (Sep 2027) only the nickname dies — never use it as a login or recovery address for anything important.

11 · Guardrails

  • Network: server binds to the Tailscale interface only; per-device tokens; QR pairing; instant revoke. Nothing listens on the public internet.
  • Approvals: only irreversible actions ask. Shell commands and file writes inside the scratch dir run free; destructive shell (deletes, force-pushes, history rewrites), writes outside the scratch dir, and sends from any mailbox other than the agent's own still ask, and the approval button carries a preview of exactly what will run or send. Reversible work — research, delegation, renames, reads, memory writes — never stops for a click.
  • Untrusted input rule: mail, web pages, and tool output are data, never instructions. The agent flags suspected prompt-injection instead of obeying it.
  • Budgets: per-day token caps per tier; free-first routing; spend ledger visible per thread; global kill switch.
  • Secrets: provider keys and mail credentials live server-side (keychain on Mac dev, mode-600 file on bb-1); never in the repo, never in the apps.
  • Data: SQLite + nightly backup; full export command; you own the bytes and the box.
